Figure 2 presents the StudentShield web application as a single process for vent screening and bullying reporting. Students supply credentials, vents, parent-hiding selections, incident details, and optional evidence. The application exchanges current vent text, a student identifier, and prior risk labels and timestamps with the external machine learning service. Counselors review cases and provide verification decisions, notes, and status updates. Super administrators also manage accounts and roles and access audit records. Parents and guardians receive notifications only when the applicable rules permit. This diagram is limited to these workflows; it does not represent the online meeting module.

[1] High-risk vents trigger counselor notification attempts. Critical vents may also trigger parent notifications, subject to parent hiding, available contact details, and applicable cooldowns. Bullying intake alerts counselors; staff verification precedes incident notifications to resolved victim or alleged-bully parent contacts. A second false-report strike has a separate reporter-parent notification path. Message delivery is not guaranteed.

Research, boundary decisions, and verification
  • One process represents the selected application boundary; external entities connect only through named, directional data flows. Internal stores and decision diamonds are omitted.
  • The custom ML service is external to this web-application boundary, although it belongs to the wider StudentShield project. MySQL, encryption, fallback rules, and internal case modules are not external entities. Parents are recipients, not authenticated portal users.
  • This is a logical context view. SMTP and SMS are delivery mechanisms for the recipient flows, not extra business actors. Hosting vendors and network infrastructure belong in the architecture diagram. The meeting workflow is explicitly outside this figure’s scope.
  • Role and flow checks: VentController.php, BullyReportController.php, AdminController.php, and the supplied capstone. Repository review does not establish live delivery performance or completed evaluation.
  • Conventions: Visual Paradigm: system context diagrams; DFD connection rules.
